## 1. Why It Is Being Created (The Problem Statement)

During severe physical trauma, internal hemorrhages, or critical surgeries, patient survival hinges entirely on the delivery speed of compatible blood:

* **Geospatial Dispatch Delays:** Traditional blood dispatch systems are slow and manually operated. They lack live, map-based visualization, forcing coordinators to call multiple hospitals and donors manually, which wastes valuable minutes in emergency scenarios.
* **The Compatibility Complexity:** Matching blood type eligibility is complex. Transfusion reactions due to type mismatches can cause lethal intravascular hemolysis. Furthermore, standard blood donors must undergo a strict 56-day medical cooldown period between donations. Manually checking compatibility against cooldown histories under pressure is prone to severe human error.
* **Cold-Chain Degradation Risks:** Blood is a highly sensitive organic tissue. It must be kept strictly within a narrow refrigeration window ($2.0\text{ }^\circ\text{C}$ to $6.0\text{ }^\circ\text{C}$) during transport. Exposure to ambient temperatures causes rapid hemolysis or bacterial growth, spoiling the supply and putting patients at severe risk.
* **Donor Privacy Vulnerabilities:** Publicly sharing donor locations, phone numbers, and addresses exposes sensitive medical data, violating health privacy laws.

## 2. What It Is Going to Solve (The Unique Solution)

LifeStream V3 coordinates emergency blood logistics by introducing a **High-Velocity GPS Radar Map**, an **AI-Assisted Dispatch Engine**, and **IoT Cold-Chain Telemetry**:

1. **Leaflet-Powered Live Radar Map:** Renders a high-fidelity interactive map visualizing emergency hospitals, nearby eligible donors, and active dispatch transports in real-time, utilizing Leaflet.js directly via CDN.
2. **Double-Factor Compatibility Gate:** Enforces biological compatibility matching alongside the mandatory 56-day cooldown check. In extreme emergencies, coordinators can toggle a "Critical Urgency" override to bypass the cooldown for vital lifesaving matches.
3. **AI Match Confidence Scoring:** Automatically computes and ranks the best donors using a geospatial-reliability formula that weighs travel distance against historical donor reliability.
4. **Active Drone/Transport Simulation:** Simulates autonomous drone dispatch routing. The backend updates the drone's GPS coordinates by 10% on each tracking request, moving it closer to the target hospital.
5. **IoT Cold-Chain Temperature Simulation:** Simulates real-time IoT temperature telemetry. It fluctuates the payload's temperature within a safe biological range ($2.5\text{ }^\circ\text{C}$ to $5.5\text{ }^\circ\text{C}$), generating alerts if the temperature slips out of compliance.
6. **Anonymized Proxy Safeguards:** Masks all donor contact data as `"hidden"` in the API layer, allowing coordinators to initiate communications via secure proxy routes without exposing personal data.

## 4. Fully Detailed Tech Stack

LifeStream V3 uses a lightweight, robust, and zero-dependency stack to ensure maximum performance and instant local setup:

* **Frontend Dashboard (Vanilla HTML5 / React CDN / Tailwind CDN):** A single-page application integrating Tailwind CSS animations and Leaflet.js maps directly in the client layer, bypassing compilation requirements.
* **Application Server (Node.js / Express 4.19.2):** High-speed API router featuring strict schemas and static front-end serving.
* **Input Validation (Zod v3.23.8):** Enforces strong type safety and parameter validation across all emergency endpoints.
* **Data Layer (JSON File Persistence):** Bypasses database overhead by utilizing atomic, serialized reads and writes to a local `db.json` database repository.
* **Geospatial Math (The Haversine Proximity Formula):** Computes precise distance vectors between donors and the emergency center:

$$a = \sin^2\left(\frac{\Delta \phi}{2}\right) + \cos(\phi_1)\cos(\phi_2)\sin^2\left(\frac{\Delta \lambda}{2}\right)$$

$$d = 2R \cdot \operatorname{atan2}\left(\sqrt{a}, \sqrt{1-a}\right)$$

*Where $R = 3958.8\text{ miles}$ (Earth's radius), $\phi$ is latitude, and $\lambda$ is longitude.*

* **AI Matching Score Formula:** Weights distance against historical donor reliability to score potential matches:

$$\text{Match Score} = (100 - (2d)) \cdot 0.5 + R_{\text{donor}} \cdot 0.5$$

*Where $d$ is distance in miles, and $R_{\text{donor}}$ is the donor's reliability score (scaled from 0 to 100).*

## 5. Phase-by-Phase Workflow Functional Description

### Phase 1: Emergency Blood Request & AI Matching

1. A coordinator registers an urgent request for a specific blood type (e.g., `O-`) with an urgency level of standard or critical.
2. The server filters the donor pool based on compatibility and cooldown states:
   * **Compatibility check:** Checks the biological chart (e.g., `O-` can donate to all types, while `AB+` can only donate to `AB+`).
   * **Eligibility window:** Ensures the donor has not donated within the last 56 days. If the request is flagged as critical, this cooldown check is automatically bypassed.
3. The server computes the distance for each eligible donor using the Haversine formula.
4. The server calculates each donor's AI Match Score and returns a sorted list of compatible matches.

### Phase 2: Autonomous Drone Dispatch Initiation

1. The coordinator selects a donor match and triggers the dispatch endpoint `/api/dispatch` with parameters:

$$\text{Payload} = \{ \text{donorId: } 1, \text{ transportType: "Drone" } \}$$

2. The server initializes a dispatch record in `db.json`, setting coordinates to the donor's location, the destination to the hospital, and launching the cold-chain temperature monitoring loop at $4.0\text{ }^\circ\text{C}$.

### Phase 3: Real-Time Telemetry Tracking Loop

1. The front-end map dashboard polls the tracking endpoint `/api/track/:dispatchId` every 1.5 seconds.
2. On each poll, the server simulates progress by moving the transport coordinates 10% closer to the destination:

$$\text{Lat}_{\text{current}} = \text{Lat}_{\text{current}} + 0.1 \cdot (\text{Lat}_{\text{target}} - \text{Lat}_{\text{current}})$$

$$\text{Lng}_{\text{current}} = \text{Lng}_{\text{current}} + 0.1 \cdot (\text{Lng}_{\text{target}} - \text{Lng}_{\text{current}})$$

3. The server updates the simulated cold-chain temperature telemetry, allowing it to fluctuate dynamically:

$$T_{\text{temp}} = T_{\text{temp}} + \delta, \quad \text{where } \delta \in [-0.25, 0.25], \text{ capped strictly between } 2.5\text{ }^\circ\text{C} \text{ and } 5.5\text{ }^\circ\text{C}$$

4. Once the transport is within 0.1 miles of the target, the server updates its status to `"Arrived"`.
